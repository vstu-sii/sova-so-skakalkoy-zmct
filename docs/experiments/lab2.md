## 2. Спайк 1 — структура против смысла даты

**Вопрос:** достаточно ли проверить тип и вид `YYYY-MM-DD`, чтобы принять дату нового мероприятия?

**Метод:** 6 заранее заданных случаев, опорная дата 2026-10-14. Проверка формы сравнивается с минимальным календарным валидатором. День недели задаётся числом вручную, а не извлекается из русского текста. Проверяем правило, а не качество LLM.

| Случай | Форма допустима | Семантический результат |
| --- | --- | --- |
| 2026-11-25, среда | Да | Допустим |
| 2026-11-25, вторник | Да | DATE_CONFLICT |
| 2025-11-25, вторник | Да | PAST_DATE |
| 2026-02-30 | Да | INVALID_DATE |
| Конец 2026-11-24 при начале 2026-11-25 | Да | END_BEFORE_START |
| Неизвестная дата (`null`) | Да | MISSING_DATE |

**Фактический результат:** 6/6 ожидаемых исходов, пять проблемных случаев прошли проверку формы и были остановлены семантической проверкой. Проверка формы здесь — простой type/regex, не полноценный JSON Schema-валидатор. Даже JSON Schema с проверкой `format` не выражает все бизнес-правила: прошедший год и несовпадение дня недели требуют отдельного контроля.

**Вердикт: не сработало.** Допущение «правильная форма означает правильный факт» отвергнуто на контрпримерах. Вывод для пайплайна — Q2 после Structured Outputs, блокировка конфликта и вопрос эксперту. Прошлый год не подставляется для подгонки дня недели.

**Ограничение:** не проверены извлечение weekday моделью, относительные даты, разные часовые пояса и статистическая частота ошибок.

## 3. Спайк 2 — перенос без потери условий

**Вопрос:** сохранятся ли неизменённые поля, если заменить карточку объектом, содержащим только новую дату и время?

**Вход:** карточка с датой 2026-11-15, временем 19:00, площадкой «Точка, Пушкина 12», ценой 2500 и скидочной ценой 2000. Правка: перенести на 2026-11-16, 15:00. Операции заданы вручную.

**Метод:** отрицательный контроль — полная замена объектом из двух полей; затем минимальный обработчик `set`/`clear` и проверка версии. Пять случаев: перенос, явное удаление скидки, set с null, устаревшая версия, повтор одного поля.

**Фактический результат:** замена теряет venue, price и price_discount. Явные операции прошли 5/5 заданных исходов: перенос сохранил три поля; clear удалил только скидку; set-null, конфликт версии и дубликат были заблокированы. API-стоимость экспериментов — 0 ₽; затраты вычислительной среды и труда в эту цифру не входят.

**Вердикт: сработало иначе.** Использовать модель для предложения частичных операций и сервер для их применения, вместо перезаписи полным результатом извлечения. Цена не становится неизвестной только потому, что её не повторили в правке.

**Ограничение:** тест не доказывает, что LLM сформирует верные операции. Проверка версии в памяти не доказывает атомарность в БД. Нужны проверка evidence, типы/диапазоны и транзакционное compare-and-swap в реализации. Код спайка намеренно покрывает только рискованный инвариант.

## 4. Что изменилось в архитектуре

1. Введён отдельный семантический контроль Q2: даты, диапазоны и конфликт календаря.
2. Правка возвращает список операций с evidence, а не новую догаданную карточку.
3. В контракт добавлены candidate_id, base/expected_version, уточнения и ручное подтверждение.
4. Генерация читает подтверждённую версию; старые тексты инвалидируются при принятии правки.
5. Режим economy закрыт до проверки качества; отсутствие API не маскируется как успешная деградация на другую модель.
