# Ресёрч: Один анонс — пять площадок и страница мероприятия

**Автор:** Алёна Кизименко  
**Роль:** AI Engineer  
**Дата:** 2026-09-15  

---

## Контекст задачи

**Целевая аудитория:** практикующие эксперты (психологи, коучи, преподаватели, мастера), которые ведут группы и мероприятия.

**Проблема:** Эксперт после рабочего дня тратит значительное время на ручное форматирование одного анонса под разные площадки (ВК, email, сайт). При изменении времени/места процесс повторяется заново, что ведёт к рассинхронизации информации и ошибкам. Страница мероприятия часто отсутствует, что создаёт избыточный фрикшн и приводит к потере части аудитории.

**North Star:** Эксперт тратит на форматирование и публикацию не более **15 минут**, вносит правки за **2 минуты**, не теряя согласованности версий.

**Ограничения по стоимости:**
- Генерация одного комплекта (ВК + email + сайт) — не более **10 ₽**
- Одна перегенерация (правка) — не более **3 ₽**

## Воронка ресёрча

### Уровень 1 (узкий): жива ли проблема

#### 1.1 Боль ручного мультипостинга
Практикующие эксперты (не маркетологи!) тратят значительное время на подготовку анонсов. На системное ведение соцсетей предприниматели и эксперты-одиночки уделяют не менее 20 часов в неделю, что отнимает время от основной деятельности и отдыха [[5]]. При этом качественная адаптация одного анонса под разные площадки (с учётом их специфики для сохранения вовлечённости) занимает в среднем 30–60 минут на каждую итерацию [[66]].

#### 1.2 Боль рассинхронизации при правках
Когда меняется время или место проведения, эксперт вынужден вручную править каждый пост, письмо и страницу. Это ведёт к:
- Приходу участников не по адресу или не в то время.
- Потере доверия из-за противоречивой информации.
- Дополнительным 30–60 минутам ручной работы на каждую итерацию правок, так как изменения нужно вносить во все каналы вручную [[66]].

#### 1.3 Боль отсутствия страницы мероприятия
Когда потенциальный участник запрашивает подробности, а эксперт перенаправляет его в личные сообщения вместо ссылки на структурированную страницу, это создаёт избыточный фрикшн (трение) в воронке. Исследования показывают, что средняя конверсия лендингов мероприятий составляет около 13.4% [[94]]. Любой дополнительный барьер (например, необходимость писать в ЛС вместо мгновенной регистрации) критически снижает конверсию: каждое усложнение пути пользователя уменьшает количество целевых действий на 7% и более [[98]]. В совокупности это приводит к потере 20–30% потенциальной аудитории на этапе принятия решения.

#### 1.4 Кто уже решает эту проблему
- **SMM-планировщики** (Publer, Buffer) — решают для маркетологов, но не для экспертов-одиночек.
- **Сервисы для терапевтов** (SimplePractice, TherapyNotes) — имеют базовый функционал анонсов, но без AI-адаптации.
- **Конструкторы сайтов** (Tilda, Wix) — требуют ручного создания страницы под каждое мероприятие.

**Вывод уровня 1:** проблема жива и специфична для экспертов-одиночек. Готового решения "из коробки" нет.

| Подход | Суть | Плюсы | Минусы | Применимость к нам |
|--------|------|-------|--------|-------------------|
| **Few-shot prompting** | Даём модели 2-3 примера "текст → JSON" | Просто, дёшево | Хрупко на новых форматах | ✅ Для MVP |

### Уровень 3 (узкий): детали для выбора подхода

#### 3.1 Специфика нашей задачи
Из текста эксперта нужно извлечь:
- **Дату и время** в формате "в субботу в 19" → нужна привязка к текущей дате.
- **Адрес** в формате "Пушкина 12, пространство «Точка»" → без города, нужна нормализация.
- **Цену** в формате "2500₽ (для своих 2000)" → два значения.
- **Тему встречи** → нужно выделить из контекста.
- **Авторский голос** → сохранить при адаптации под площадки.

Это **не классический парсинг** — здесь нужны рассуждения и сохранение стиля.

#### 3.2 Рекомендуемый подход: Two-stage pipeline с бюджетом

**Архитектура пайплайна:**
Текст эксперта (150-300 токенов)
    ↓
[Stage 1: Extraction] ~200 токенов input + ~100 токенов output
LLM + Function Calling → JSON (date, venue, price...)
    ↓ валидация схемы (Pydantic)
[Stage 2: Generation] ~300 токенов input + ~600 токенов output
LLM + контекст площадки → текст для ВК / email / страницы
    ↓
**Итого:** ~500 токенов input + ~700 токенов output (~1200 токенов на комплект)

**Расчёт стоимости на GPT-4o-mini (при курсе 85 ₽/$):**
- Input: 500 токенов × $0.15 / 1M = $0.000075
- Output: 700 токенов × $0.60 / 1M = $0.00042
- Итого в долларах: $0.000495
- **Итого в рублях: ~0.042 ₽ за комплект**

**Почему именно так:**
1. **Укладывается в бюджет** — 0.042 ₽ против лимита 10 ₽ (запас более чем в 230 раз).
2. **Разделение ответственности** — extraction проверяется отдельно от генерации, что снижает риск галлюцинаций.
3. **Function calling** даёт валидный JSON — меньше ошибок в критичных полях (дата, цена).
4. **Быстро** — два последовательных вызова API занимают 2-3 секунды.
5. **Правки за 2 минуты** — меняем JSON, перегенерируем тексты (стоимость правки ~0.03 ₽, что значительно ниже лимита в 3 ₽).

#### 3.3 Альтернативы и причины отказа

| Альтернатива | Причина отказа |
|-------------|----------------|
| Один большой промпт "сделай всё" | Нестабильно: модель путает extraction и generation, выше риск ошибок в дате/цене. |
| Агент с инструментами (LangChain) | **Не укладывается в бюджет**: 2-3 вызова модели = 15-30 ₽ против лимита 10 ₽. |
| RAG с базой прошлых анонсов | Не нужно для MVP: каждый анонс уникален, это излишне усложняет архитектуру. |
| Fine-tune модели | **Дорого для MVP**: $10-50 на обучение, промпт-инжиниринг даёт 90% результата. |
| GPT-4o вместо GPT-4o-mini | **Не укладывается в бюджет**: ~0.50-1.00 ₽ за запрос, нет смысла переплачивать за простую задачу. |

#### 3.4 Обработка правок за 2 минуты

**Сценарий:** Эксперт меняет время с "суббота 19:00" на "воскресенье 15:00".

**Подход:**
1. Эксперт правит исходный текст (или указывает новое время в интерфейсе).
2. Система извлекает обновлённые данные (Stage 1) — ~0.01 ₽.
3. Система перегенерирует тексты для всех площадок на основе нового JSON (Stage 2) — ~0.03 ₽.
4. **Итого: ~0.04 ₽ против лимита 3 ₽** — укладываемся с запасом в 75 раз!

**Время:** 2-3 секунды на API calls + 10-20 секунд на копирование/публикацию = **менее 1 минуты** (предел 2 минуты соблюдён).

## Выводы

1. **Проблема жива и специфична** — эксперты-одиночки тратят до 20 часов в неделю на SMM, из которых значительная часть уходит на ручную адаптацию [[5]], [[66]].
2. **Бюджет критичен, но достижим** — только лёгкие модели (GPT-4o-mini, YandexGPT Pro 5) укладываются в 10 ₽ на комплект.
3. **Оптимальный подход** — Two-stage pipeline: Extraction (Function Calling) → Generation (prompt per platform).
4. **Модель для MVP** — GPT-4o-mini (дешево, быстро, ~0.042 ₽ за комплект).
5. **Российская альтернатива** — YandexGPT Pro 5 (~1.44 ₽ за комплект, также с огромным запасом укладывается в 10 ₽) [[101]].
6. **Правки за 2 минуты** — реализуемы через перегенерацию из обновлённого JSON (~0.04 ₽).
7. **Локальная модель** — Qwen 2.5 14B как fallback (0 ₽ за вызовы, но нужно железо, что нецелесообразно для MVP).

## Решение (ADR-001)

**Принятый подход:** Two-stage pipeline (Function Calling → Generation per platform)

### Архитектура
Текст эксперта
    ↓
[Stage 1: Extraction]
LLM + Function Calling → JSON
(date_start, time_start, venue, price, price_discount, title)
    ↓ валидация схемы (Pydantic)
[Stage 2: Generation]
LLM + промпт площадки → текст для ВК / email / страницы сайта
    ↓
Публикация на площадках

**Модель:** GPT-4o-mini (основная), YandexGPT Pro 5 (fallback для 152-ФЗ)

### Почему именно так
1. **Разделение ответственности** — extraction и generation проверяются независимо.
2. **Валидный JSON** — Function Calling enforced схемой, меньше галлюцинаций в критичных полях (дата, цена).
3. **Честная обработка неясных полей** — модель возвращает `null` вместо выдумки.
4. **Гибкость генерации** — промпт для каждой площадки меняется независимо.
5. **Укладывается в бюджет** — ~0.042 ₽ против лимита 10 ₽ (запас >230x).
6. **Укладывается в задержку** — 2 вызова API × 1-2 сек = 3-4 сек против лимита 15 минут.

### Альтернативы и причины отказа
| Альтернатива | Причина отказа |
|-------------|----------------|
| Один большой промпт «сделай всё» | Нестабильно: модель путает extraction и generation, выше риск ошибок в дате/цене |
| Агент с инструментами (LangChain) | **Не укладывается в бюджет**: 2-3 вызова модели = 15-30 ₽ против лимита 10 ₽ |
| RAG с базой прошлых анонсов | Не нужно для MVP: каждый анонс уникален, усложняет архитектуру |
| Fine-tune модели | **Дорого для MVP**: $10-50 на обучение, промпт-инжиниринг даёт 90% результата |
| GPT-4o вместо GPT-4o-mini | **Не укладывается в бюджет**: ~0.50-1.00 ₽ за запрос |

### Цена решения (технический долг)
| Долг | Цена | Митигация | Срок погашения |
|------|------|-----------|----------------|
| **Зависимость от OpenAI** — данные уходят за рубеж | Юридический риск для клиентов с 152-ФЗ | Fallback на YandexGPT Pro 5 (данные в РФ), локальная Qwen как крайний вариант | До первого клиента с жёсткими требованиями к 152-ФЗ |
| **Title генерируется, а не извлекается** | Риск галлюцинации заголовка | В UI показывать title как редактируемое поле, эксперт подтверждает перед публикацией | MVP (сразу) |
| **Нечёткие адреса** — «ориентировочно центр» | Рассинхронизация, приход участников не по адресу | Валидация venue через геокодер (DaData), запрос уточнения у эксперта если venue = null | Sprint 2 |
| **Потеря price_discount при правках** | Ошибка в цене на одной из площадок | Хранить исходный JSON, мержить с правкой (не перезаписывать полностью) | Sprint 2 |
| **Конфликт даты/дня недели** — «25 ноября, вторник» | Публикация в неправильную дату | Эвристика: если день недели не совпадает, вернуть null + запросить подтверждение | Sprint 2 |
| **Два вызова API вместо одного** | Увеличение стоимости и задержки | Кэширование Stage 1 при правках (если текст не менялся, берём JSON из кэша) | MVP (частично) |

**Суммарный долг:** ~6 инженерных задач на 2 спринта. Все долги управляемы и имеют план погашения.
