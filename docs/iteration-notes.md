# Итоги прототипирования и план следующего спринта

**Дата:** 30.10.2026  
**Основание:** анализ PR #13, PR #14, Delivery Lab 3, существующего eval report и исходников UI/API; ручной прогон пользовательского интерфейса Product / VO от 30.10.2026 (`docs/product/use-cases/validation-run.md`).  
**Статус фактов:** выводы ниже подтверждаются переданными архивами; оценки трудоёмкости — плановые экспертные оценки, а не фактический учёт времени.

## 1. Что изменилось после прототипа

### Подтверждено реализацией

- Есть Next.js UI для эксперта: dashboard, форма нового анонса, preview извлечённых полей, публичная страница, форма регистрации, профиль.
- В Delivery UI форма отправляет текст в `POST /extract` сервиса `services/extractor`.
- Legacy extractor использует регулярные выражения для даты/времени/места/цены и пытается сохранить событие в PostgreSQL.
- Есть page-composer endpoint, но его `load_event()` возвращает фиксированный демонстрационный объект, а не запись из БД.
- VK publisher и mailer отвечают `not_implemented`.
- Registration endpoint отвечает `TODO: implement registration`; фактическое сохранение заявки не реализовано.
- В отдельной ветке PR #14 существует AI baseline: FastAPI API, Qwen 2.5 3B через Ollama, JSON Schema validation, owner-scoped SQLite store, Bearer token, Idempotency-Key, подтверждение кандидата и генерация черновиков только после подтверждения.
- AI API PR #14 не подключён к `frontend/lib/api.ts`: фронтенд использует другие URL и другой контракт.
- Quality провёл baseline на 53 примерах × 3 повтора (159 вызовов; 153 в основных метриках) и отдельный mini pipeline на 6 примерах.

### Не подтверждено / не реализовано

- Сквозной сценарий от текста анонса до трёх опубликованных каналов.
- Синхронное изменение времени/места после публикации.
- Исправление опубликованного текста с контролем ручных overrides.
- Сохранение и передача реальной заявки участника эксперту.
- Полная сборка страницы из библиотеки блоков и обработка изображений.
- Человеческие оценки качества генерации (M4/M5), фактическая стоимость локального оборудования и T1 до публикации.


### Результаты ручной проверки интерфейса Product / VO (30.10.2026)

Эти наблюдения получены отдельно от Quality benchmark и относятся к одному ручному примеру анонса.

- В форме нового анонса открывается поле для текста; отдельное поле заголовка, выбор даты и загрузка/сортировка изображений в проверенном интерфейсе не обнаружены.
- На тексте с фразой «В пятницу в 18:30… в точке кипения (пр-кт Ленина 28а)… Плата за вход 300р» дата/время и цена определились верно по наблюдению автора прогона; место интерфейс показал как «Не найдено».
- После ручной корректировки данные отображались верно; сохранение после повторного открытия не проверялось.
- Полный комплект из трёх материалов, предпросмотр и публикацию через UI выполнить не удалось.
- В UC-02 и UC-03 пользовательские функции редактирования опубликованного анонса не обнаружены, поэтому эти сценарии не выполнены.
- В UC-04 страница участника открылась; данные визуально совпали с ожидаемыми. На форме есть поля имени и email, но отправка, сохранение заявки и передача эксперту не подтверждены.

**Интерпретация:** это ручные наблюдения UI, а не измерения E2E и не дополнительная выборка Quality. Время сценариев не измерялось. Не следует выводить из этих наблюдений статистическую точность модели или утверждать, что публикация/регистрация работают.

## 2. Главные продуктовые выводы

1. **Прототип проверил техническую осуществимость частей, но не целостность продукта.** AI baseline и Delivery UI существуют параллельно; ручной UI-прогон подтвердил частичное извлечение на одном примере, но не полный сценарий публикации.
2. **Качество фактов — главный риск.** M2 = 62.7%, M3 = 29.4%, venue accuracy = 54.2%, false-fill M6 = 10.4%. В отдельном ручном примере UI не нашёл место («Не найдено»), хотя оно присутствовало во входном тексте; это единичное наблюдение, не новая метрика.
3. **Пустое значение предпочтительнее выдуманного.** Для даты, места и цены нужен блокирующий вопрос, если уверенного значения нет.
4. **Публикация и регистрация — не просто интеграционные детали.** Пока эти операции заглушки, UC-01 и UC-04 нельзя принимать как сквозные.
5. **Сначала нужно соединить контракты.** Нельзя одновременно развивать два независимых extraction API без явного решения о едином source of truth.

## 3. План следующего спринта

Оценки приведены в человеко-часах и включают разработку и базовые тесты; это плановые допущения. Приоритеты: P0 — блокирует достоверность/сквозной сценарий; P1 — важно для следующего демо; P2 — можно отложить.

| Приоритет | Задача | Владелец | Оценка | Цена откладывания / техдолг |
|---|---|---|---:|---|
| P0 | Выбрать единый extraction contract и подключить Delivery UI к AI API (или официально оставить regex baseline); описать адаптер и error states | AI Engineer + Delivery | 6–10 ч | Два разных результата извлечения; eval не отражает пользовательский путь |
| P0 | Календарный resolver: `reference_date`, timezone, относительные дни; month-only → null; «как обычно» → null | AI Engineer | 6–8 ч | Риск неверной даты/места в публичной карточке |
| P0 | Подтверждение критичных полей в UI: дата, место, цена; для «место не найдено» показать явное состояние и ручной ввод; блокировка генерации до подтверждения | Product + Frontend + AI | 5–8 ч | Модельные ошибки превращаются в видимые пользователю факты; ручной прогон уже показал пропуск места |
| P0 | Регистрация: сохранить заявку в БД, вернуть registration ID, только затем показывать успех | Delivery | 6–10 ч | Ложное подтверждение записи; заявка теряется |
| P1 | Подключить page-composer к событию из БД, убрать hard-coded demo event; тест отсутствующих полей | Delivery | 4–6 ч | Публичная страница показывает не то событие |
| P1 | Реализовать публикационный adapter interface и статусы каналов; начать с sandbox/mock provider, не выдавать за реальную публикацию | Delivery | 8–12 ч | UC-01 остаётся недостижимым; сложно измерить E2E |
| P1 | Regression suite для даты/места/цены/free/tariffs и adversarial prompts; новый prompt version и сравнение с test split | Quality + AI | 4–6 ч | Регрессии не обнаруживаются до демонстрации |
| P1 | Заполнить human review 18 черновиков, посчитать M4/M5 с инструкцией и согласованной шкалой | Product + Quality | 2–4 ч | Нельзя оценить полезность/редактируемость генерации |
| P2 | Версионирование исходного анонса и diff для будущих UC-02/UC-03 | Product + Delivery | 6–10 ч | Правки и рассинхронизация каналов останутся ручными |
| P2 | Загрузка/порядок изображений, page block library, проверка M8/M9 | Delivery | 8–14 ч | Полный комплект материалов и визуальная страница не готовы |

### Рекомендуемый scope спринта

Не брать всё сразу. Рекомендуемый обязательный scope: первые четыре P0 задачи плюс regression suite. Если команда состоит из нескольких владельцев, UI integration, resolver и регистрация могут идти параллельно. Публикацию в реальные VK/email лучше не включать, пока не готовы подтверждение фактов, статусы ошибок и sandbox-проверка.

## 4. Definition of Done следующей итерации

- Один документированный контракт извлечения используется пользовательским UI и eval harness.
- Все критичные поля либо имеют подтверждённое значение, либо остаются null с blocking question.
- Тесты покрывают relative dates, month-only, context-only venue, free price и multi-tier pricing.
- Публичная страница читает данные по event ID из БД, а не из константы.
- Registration success отображается только после успешного сохранения заявки.
- M2/M3/M6/S1 публикуются рядом с latency; M4/M5 не публикуются без human review.
- Никакой тестовый provider не обозначается как реальная публикация.

## 5. Риски и решения, которые нужно принять

- **Архитектурное решение:** AI API PR #14 и Delivery services сейчас имеют разные контракты и хранилища. Нужен явный ADR: интегрировать AI API в Delivery или перенести его функциональность в сервисную архитектуру.
- **Безопасность:** S1 = 53.3% по текущему extraction test; автоматическая публикация недопустима.
- **Эксплуатация:** локальный Ollama baseline имеет нулевую внешнюю API-плату, но полная стоимость владения не рассчитана.
- **Данные:** owner scoping и токены присутствуют в AI teaching service, но production readiness, multi-worker safety и production DB отдельно не доказаны.
- **Фронтенд:** версия Next.js и security advisories требуют отдельного dependency review; в этой работе не утверждается конкретная уязвимость без отдельной проверки advisory и lockfile.

## 6. Что считать результатом лабораторной

Прототип показал, что можно получить структурированный кандидат и подготовить черновики, но не доказал, что продукт безопасно публикует комплект и обслуживает участника end-to-end. Следующий спринт должен закрыть разрыв между измеренным AI baseline и реальным Delivery UI, а также исключить тихую выдумку критичных фактов.
