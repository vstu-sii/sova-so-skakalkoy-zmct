# UC-04. Участник открывает страницу мероприятия

**Актёр:** потенциальный участник
**Вторичный актёр:** эксперт

---

## Цель

Узнать все условия мероприятия и записаться, не вступая в переписку.

## Контекст

Участник увидел пост во ВКонтакте или письмо и хочет подробностей: во сколько, где, сколько стоит, как попасть. Сегодня это заканчивается вопросом в личные сообщения, на который эксперт отвечает между приёмами.

Оговорка по доказательной базе: прямой связи «нет страницы — участники теряются» интервью не подтвердили. Данила: «такого ни разу не было», Алла: «они не теряли, но риски есть, риски сохраняются». Поэтому сценарий существует не ради борьбы с оттоком, а ради того, чтобы у мероприятия был один адрес, где написана правда и где правка из UC-02 применяется мгновенно.

## Предусловия

- Анонс опубликован по UC-01.

## Основной сценарий

1. Участник нажимает ссылку в посте или письме.
2. Система открывает страницу мероприятия.
3. Участник видит название, дату, время, место, цену и описание — ровно те значения, которые эксперт подтвердил при публикации.
4. Участник нажимает «Записаться».
5. Система показывает форму записи.
6. Участник оставляет контакт для связи.
7. Система подтверждает запись на экране.
8. Система передаёт заявку эксперту.

## Альтернативы

**3а. Какое-то значение не указано.** Соответствующий блок на странице отсутствует. Пустых мест и надписей «не указано» на странице не бывает.

**4а. Мероприятие уже прошло.** Кнопка записи не показывается, вместо неё отметка, что мероприятие состоялось.

## Исключения

**Э1. Страница открыта по старой ссылке после изменения времени.** Участник видит актуальные значения: адрес страницы постоянный, содержимое обновляется.

## Результат

Участник знает условия и оставил заявку, не написав эксперту ни одного сообщения. Эксперт получил заявку с контактом.

## Связь с метриками

- Соответствие данных на странице эталону — M8 и M1 по критичным полям.
- Актуальность после правки — страница обязана показывать новые значения сразу после UC-02.

## Открытый вопрос

Что происходит с заявками дальше — список в системе, письмо эксперту, выгрузка — в первой версии не решено. Сбор подтверждений и работа с участниками вынесены в не-скоуп, см. `docs/roadmap.md`.

## Источник

PRD, боль 3. Данила: «Для небольших камерных мероприятий до 50 человек полноценный сайт делать нет смысла» — поэтому страница обязательна как источник правды, но не позиционируется как средство привлечения.

## Версия после прототипа — явные изменения (v2, 30.10.2026)

**Статус:** в ручном прогоне интерфейса 30.10.2026 страница открылась, и отображаемые данные визуально совпали с ожидаемыми. Связь страницы с реально опубликованным событием отдельно не подтверждена; отправка и сохранение заявки не проверены.

### Что уточнено

| Было (v1) | Стало (v2) | Причина |
|---|---|---|
| Шаг 2–3: открыть страницу и увидеть подтверждённые данные | Страница должна загружать событие по ID из постоянного URL; demo/static fallback не считается успешным результатом | В ручном прогоне страница открылась и данные визуально совпали, но источник данных/сквозная связь не проверены; в коде composer обнаружен demo fallback |
| Шаг 6: оставить контакт | Форма проверяет имя/email/consent, затем сервер сохраняет заявку и возвращает registration ID | Текущий register endpoint — TODO-заглушка |
| Шаг 7: система подтверждает запись | Экран успеха показывается только после подтверждённой записи в хранилище; ответ заглушки не является успехом | Сейчас UI считает любой успешный HTTP-ответ подтверждением |
| Шаг 8: передать заявку эксперту | Владелец/эксперт должен видеть заявку или получить уведомление; пока это не реализовано | В backend нет сохранения/уведомления |

### Новые правила поведения

- Если событие не найдено, закрыто или прошло, страница показывает явный статус, а не демо-данные.
- Если поле отсутствует, блок скрывается; неизвестное значение нельзя подменять тестовым.
- Повторная отправка формы должна быть идемпотентной, чтобы не создавать дубликаты заявок.
- Успешная запись должна быть проверяема по registration ID.

### Наблюдение ручного прогона интерфейса (30.10.2026)

Страница участника открылась; по визуальному сравнению отображаемые данные совпали с теми, которые ожидались после создания анонса. При этом связь страницы с сохранённым событием и подтверждённой публикацией отдельно не проверялась. На форме обнаружены поля имени и email. Фактическая отправка заявки, сохранение в БД, показ подтверждения и передача заявки эксперту не подтверждены.

Проверка обновления страницы по старой ссылке после UC-02 не проводилась, поскольку UC-02 не удалось выполнить.
