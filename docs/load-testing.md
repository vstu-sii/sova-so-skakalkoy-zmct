## 1. Профиль нагрузки по сценариям UC (Demo Day)

Целевой сценарий — пик демонстрации (Demo Day): аудитория одновременно открывает публичные страницы мероприятий, часть посетителей записывается на событие, эксперты обновляют дашборд, создают и публикуют анонсы.

| Сценарий UC | Операция / эндпоинт | Доля трафика (смешанный профиль) | Сервис | Характер нагрузки |
|---|---|---:|---|---|
| **UC-04** | Просмотр публичной страницы (`GET /events/{id}`) | 70% | `extractor` → PostgreSQL | Чтение БД (PK lookup + count подписчиков) |
| **UC-04** | Запись участника без авторизации (`POST /subscribe`) | 15% | `extractor` → PostgreSQL | Запись в `subscribers` (UNIQUE constraint) |
| **UC-01** | Дашборд эксперта (`GET /events`, JWT) | 10% | `extractor` → PostgreSQL | JWT-валидация + агрегация событий и публикаций |
| **UC-04** | Сборка блоков страницы (`POST /compose`) | 5% | `page-composer` | Stateless JSON-генерация |
| **UC-04 (SSR)** | Отрисовка Next.js страницы (`GET /event/{id}`) | отдельный замер | `site` (Next.js 16) | SSR HTML |
| **UC-01 (VK)** | Публикация поста (`POST /publish`, mock) | отдельный замер | `vk-publisher` → PostgreSQL | Запись в `publications` + обновление `events` |
| **UC-01 (AI)** | Извлечение сущностей из текста (`POST /extract`) | отдельный замер | `extractor` → Ollama (`qwen2.5:1.5b`) | CPU/RAM-bound LLM инференс (`OLLAMA_NUM_PARALLEL=1`) |

## 3. Найденный предел системы

1. **Контур API + БД (`extractor`, `page-composer`, PostgreSQL):**
   - **Точка насыщения (knee):** наступает при `c ≈ 20` параллельных клиентов на уровне **~400–420 RPS**.
   - При росте параллельности с 20 до 100 пропускная способность остаётся на плато (~421 RPS), а медианная латентность линейно растёт со 46 мс до 241 мс (`p95 = 266 мс`) при **0% ошибок** (ни одного `5xx` или таймаута пула).
   - Для Demo Day (ожидаемый пик: 20–50 одновременных пользователей, ~10–30 RPS) запас по производительности — **>10×**.

2. **Контур фронтенда (`site`, Next.js 16):**
   - Устойчиво держит **~131 RPS** при `c=20` (`p95 = 339 мс`, 0% ошибок). Для Demo Day запас **>5×**.

3. **Контур локальной LLM (`POST /extract` → Ollama `qwen2.5:1.5b`):**
   - **Жёсткий предел:** **~0.10–0.14 RPS (~6–8 извлечений в минуту)** при `OLLAMA_NUM_PARALLEL=1`, `mem_limit: 2g`, `cpus: 2.0`, `OLLAMA_KEEP_ALIVE=0`.
   - Первый/холодный вызов занимает до **14.9 с** (подгрузка весов модели с диска), тёплые вызовы — **~7.4–8.1 с**.
   - При одновременной отправке `N` запросов они выстраиваются в очередь `llm_lock`, и время ответа растёт примерно на `+7.5 с` на каждый запрос в очереди (`c=3` → `p95 = 22.2 с`). При очереди `>22–24` одновременных вызовов сработает `LLM_OVERALL_TIMEOUT=180 с`, после чего запрос штатно деградирует в regex-парсер (~5 мс, HTTP 200).

## 4. Узкие места: план устранения или обоснование «ок»

| Узкое место | Причина | Влияние на Demo Day | Решение / статус |
|---|---|---|---|
| **1. Последовательная очередь Ollama (`0.10–0.14 RPS`)** | `OLLAMA_NUM_PARALLEL=1`, `llm_lock`, `OLLAMA_KEEP_ALIVE=0`, лимит контейнера 2 ГБ RAM / 2 CPU (ADR-006) | Низкое: извлечение запускают только эксперты (1–3 человека), посетители LLM не трогают | **Обоснование «ок» для MVP/Demo Day:** защита от OOM на локальной/бюджетной машине; при переполнении очереди или падении модели срабатывает regex-fallback. **План на прод:** выставить `OLLAMA_KEEP_ALIVE=5m` (уберёт холодные ~7 с), либо переключить `OLLAMA_URL` на GPU-хост / облачный LLM API. |
| **2. Плато `extractor` на ~420 RPS** | Один процесс `uvicorn` (`--workers 1`) + синхронный пул SQLAlchemy (`pool_size=10, max_overflow=20`) | Нет влияния: запас >10× относительно Demo Day | **Обоснование «ок» для MVP:** 0% ошибок даже при `c=100` (`p95 = 266 мс`). **План на рост:** запуск 2–4 воркеров `uvicorn` за `api-gateway` (Nginx) + кэширование `GET /events/{id}` в Redis на 30 с. |
| **3. Одиночный процесс Next.js (`~131 RPS`)** | SSR в одном контейнере Node.js | Нет влияния: запас >5× | **Обоснование «ок»:** достаточно для Demo Day; в проде масштабируется репликами или CDN-кэшем публичных страниц `/event/[id]`. |
| **4. Блокирующие внешние вызовы в `vk-publisher` / `mailer`** | Синхронные HTTP/SMTP вызовы в обработчиках запросов | Низкое: кнопки нажимает только эксперт; таймауты и ретраи ограничены (`15–20 с`, 1 ретрай) | **Обоснование «ок» для MVP.** **План на прод:** вынести массовые рассылки (>50 подписчиков) в фоновую очередь Redis/Celery. |
