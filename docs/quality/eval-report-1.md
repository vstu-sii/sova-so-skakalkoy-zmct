# Eval report 1 — где прототип ошибается

**Дата:** 30.10.2026  
**Владелец документа:** Product / VO  
**Источники:** `docs/quality/reports/lab3.md`, `docs/quality/reports/lab3-full/requests.jsonl`, `docs/experiments/lab3.md`, исходники Delivery и AI baseline PR #14.

## 1. Краткий вывод

Baseline технически выполняет извлечение и генерацию черновиков, но не готов к публикации без проверки экспертом. Ключевой риск — не HTTP-ошибка, а правдоподобное неверное значение критичного поля. Валидный JSON и успешный ответ API не гарантируют правдивость даты, места или цены.

Отдельный продуктовый риск: AI baseline из PR #14 не подключён к пользовательскому UI Delivery. Delivery UI вызывает другой, regex-based extractor. Следовательно, нельзя считать, что пользовательский сценарий уже получает результаты, измеренные в Quality eval.

## 3. Ошибки, которые имеют разную цену

### 3.1. Выдуманная дата из месяца — критическая ошибка

Пример из `gd-0003`: пользователь указывает только месяц, модель выводит первое и последнее число месяца. Пользователь не сообщал конкретный день. Это false-fill, который может привести к неверной записи в календарь и публикации ложного расписания.

**Решение:** месяц без дня должен давать `date_start = null` и blocking clarification. Запрещено автоматически выбирать 1-е число или диапазон месяца.

### 3.2. Неверное разрешение относительной даты — критическая ошибка

Пример `gd-0001`: «в субботу» при reference date 14.11.2025 превращается в 19.11 вместо 15.11; одновременно потеряно слово «Пространство» в названии места.

**Решение:** относительные даты вычислять детерминированным календарным resolver с явно переданными `reference_date` и `timezone`; модель не должна сама угадывать календарную дату. До разрешения неоднозначности — блокирующий вопрос.

### 3.3. Неизвестное прошлое контекстное значение превращается в выдумку

Пример `gd-0004`: при фразе, требующей прошлого контекста, модель придумала 18:00 и полный адрес. Это опаснее, чем пустое поле: UI может показать выдумку как подтверждённый факт.

**Решение:** неизвестный контекст → null + вопрос. Фразы «как обычно», «там же», «в прошлый раз» никогда не должны преобразовываться в адрес без сохранённого и доступного подтверждённого контекста.

### 3.4. Потеря части названия/адреса — переменная тяжесть

В `gd-0001` и `gd-0006` упрощено название/адрес. Если теряется название площадки, это может привести к выбору другого места; если удалена только необязательная пунктуация, риск ниже.

**Решение:** сравнивать нормализованный адрес, но отдельно проверять сохранность идентифицирующего названия площадки. Нельзя объединять все ошибки venue в одну категорию «адрес не совпал».

### 3.5. Бесплатное событие и нулевая цена

Пример `gd-0005`: бесплатный вебинар не получает нулевую стоимость. В dataset v2 M1 для price = 79.6%; отсутствие цены в карточке может быть ошибочно воспринято как неизвестная цена, а не бесплатный вход.

**Решение:** `free` / `бесплатно` / `вход свободный` должны приводить к `price = 0` и отдельному типу `free`; UI обязан явно показывать «Бесплатно», а не скрывать блок как неизвестный.

### 3.6. Цена и тарифы

Общая точность price — 79.6%, а discount price — 96.5%, но эти знаменатели различаются. Перепутанные базовый и льготный тарифы могут привести к прямой финансовой потере. Нельзя выводить из высокого процента discount price, что весь прайс безопасен.

**Решение:** хранить тарифы как пары `{label, amount}` с исходным текстовым фрагментом; показывать все тарифы на проверку; блокировать генерацию, если суммы конфликтуют или не удаётся однозначно связать цену с категорией.

### 3.7. Prompt injection

S1 extraction = 16/30 = 53.3% по forbidden-string check. Это означает, что текущая защита недостаточна. При этом сама метрика — консервативный тест по строкам, а не доказательство всех возможных атак.

**Решение:** рассматривать исходный текст как недоверенные данные; структурировать разделение инструкций/данных; не давать модели инструментов публикации; проверять выход схемой и политиками; обязательное подтверждение человеком. Повторить adversarial suite после изменения промптов.


## 3.8. Ручное наблюдение Product / VO в интерфейсе (30.10.2026)

Отдельно от Quality benchmark выполнена ручная проверка одного текста анонса через пользовательский интерфейс сайта:

> «В пятницу в 18:30 собираемся в точке кипения (пр-кт Ленина 28а). Будем разбирать проблемы проекта. Плата за вход 300р.»

Наблюдение:
- дата/время определились верно по оценке автора прогона;
- цена `300р` определилась верно;
- место не было найдено: интерфейс показал «Не найдено», хотя название «Точка кипения» и адрес присутствовали во входном тексте;
- после ручной корректировки данные отображались верно; сохранение после повторного открытия отдельно не проверялось.

Это **один ручной пример через UI**, а не часть набора из 159 запросов Quality, не независимая оценка точности и не основание пересчитывать M1/M2/M3/M6. Он согласуется с тем, что venue является рискованным полем в benchmark, но не должен объединяться с benchmark-метриками в одну статистику.

Также при ручной проверке UI не были обнаружены отдельное поле заголовка, выбор даты и загрузка/сортировка изображений. Полный комплект из трёх материалов и публикацию проверить не удалось. В UC-04 страница участника открылась, визуально ожидаемые данные совпали; наличие формы имени/email подтверждено, но отправка и сохранение заявки не проверены. UC-02 и UC-03 не удалось выполнить через UI, поскольку пользовательские функции редактирования опубликованного анонса не обнаружены.

## 4. Разделение ответственности между Quality и Product

Quality отвечает за воспроизводимые числа, эталоны, scorers, raw outputs, CI и классификацию технических сбоев. Product отвечает за тяжесть ошибки для пользователя, допустимость блокировки, приоритет исправления и формулировку интерфейсного вопроса.

Примеры:
- потеря запятой в адресе может быть малозначимой, если площадка однозначно распознаётся;
- потеря названия пространства может быть критичной, даже если строковое сходство высокое;
- неверная дата и цена — критичны независимо от того, насколько «правдоподобно» выглядит ответ;
- null для неизвестного значения обычно безопаснее, чем правдоподобная выдумка.

## 5. Рекомендации и критерии допуска

1. Не публиковать автоматически результаты модели. Сохранять blocking clarification и явное подтверждение экспертом.
2. Детерминированно вычислять относительные даты; месяц без дня и неизвестный контекст оставлять пустыми.
3. Ввести отдельные проверки для названия площадки, адреса, нулевой цены и нескольких тарифов.
4. Не считать `E3` показателем качества. На dashboard рядом должны стоять M2/M3/M6/S1.
5. Не заявлять M4/M5, пока не заполнен human review для 18 черновиков.
6. Не заявлять качество полного сценария, пока UI Delivery не подключён к AI API PR #14 и реальная регистрация/публикация не реализованы.
7. После исправлений поднять новый `prompt_version`, прогнать тот же test split без изменения эталонов и сравнить с baseline.

**Вывод для приёмки:** baseline годится как инженерный прототип для экспериментов и подготовки черновиков под обязательным контролем эксперта. Он не готов к автономному использованию в сценариях, где дата, место или цена становятся публичным обещанием.
