# Тест-план

**Проект:** Один анонс — площадки и страница мероприятия
**Статус:** v1 — на согласовании/
**Обновлено:** 2026-10-14

---

## 1. Принцип

Всё, что можно проверить кодом без модели, проверяется кодом без модели. Модель оценивается только там, где её ответ нельзя вычислить: качество извлечения на реальных формулировках и пригодность текста. Поэтому уровней три, и стоят они в порядке цены и надёжности.

| Уровень    | Модель                                             | Что гарантирует                                  | Цена и скорость                 |
| ---------- | -------------------------------------------------- | ------------------------------------------------ | ------------------------------- |
| Unit       | нет                                                | детерминированная логика вокруг модели           | миллисекунды, 0 ₽               |
| Интеграция | записанные ответы (fixtures), ВК и SMTP — заглушки | сервисы правильно связаны, отказы обрабатываются | секунды, 0 ₽                    |
| Evals      | настоящая                                          | качество и безопасность на golden dataset        | минуты, ≈7 ₽ за прогон (см. §6) |

## 2. Что тестируем на каждом уровне

### 2.1 Unit (без модели)

| Модуль | Что проверяем | Метрика |
|---|---|---|
| extractor, схема | JSON Schema `event.schema.json` принимает все `expected` из датасета и отклоняет: пустую строку вместо `null`, `price` числом, формат `19.00`, дату `2026-13-40` | A1, A2 |
| extractor, нормализация | сравнение «после нормализации»: «в 19» = `19:00`, регистр и краевые пробелы в `title`, «Пушкина 12» = «ул. Пушкина, 12» | M1 (код сравнения) |
| extractor, правило `null` | при пустом поле во входе в результат не подставляется значение по умолчанию (`format: offline`) | M6 |
| резолвер относительных дат (если вынесен в код) | «завтра», «в субботу», «на следующей неделе, во вторник» от `published_at`; граница месяца и года; «в субботу» при публикации в субботу фиксируется как отдельный случай | M1 по `date_start` |
| нормализатор цены | «2500 (для своих 2000)» → две ставки; «бесплатно» → `0`; «по желанию» → `donation`; полноширинные цифры «２５００» и пробелы-разделители тысяч | M1 по `price` |
| линтеры площадок | ВК и email: длина, разметка, положение ссылки, число картинок в карусели, пропорции; граничные значения лимитов (лимит, лимит+1) | M7 |
| page-composer | состав блоков по правилу; ни одного пустого плейсхолдера `{{...}}`; поля подставлены экранированно | M8 |
| media | порядок картинок сохраняется; дублей и потерь нет; превышение лимита даёт ошибку, а не обрезку молча | M9 |
| publish gate | публикация без статуса `approved` отклоняется; `approved` привязан к хэшу черновика, правка черновика сбрасывает его | S2 |
| кэш | ключ содержит `expert_id` и версию промпта; два эксперта с одинаковым текстом получают разные записи | безопасность (LLM02) |
| логирование | на каждый запрос записаны `request_id, model, prompt_tokens, completion_tokens, latency_ms, cost_rub` | E1, E2 |
| подсчёт метрик | сам скрипт evals: формула Wilson против эталонных значений из справочника; M2 считает «хотя бы одно из пяти критичных полей» | все |

Датасет сам тоже под тестом: `scripts/validate_golden.py` и негативный тест (набор заведомо сломанных записей даёт ошибки, а не «OK»).

### 2.2 Интеграция

Ответы модели берутся из записанных fixtures (`tests/fixtures/llm/*.json`), поэтому тест не зависит от провайдера и не стоит денег. Fixtures обновляются явной командой и ревьюятся как код.

| Сценарий | Проверка |
|---|---|
| Счастливый путь: анонс → extractor → composer → черновики ВК, письмо, страница | в странице и черновиках дата, место, цена равны извлечённым (M8, согласованность площадок) |
| Невалидный JSON от модели | один повтор, затем ошибка E3, ничего не публикуется |
| Таймаут и 5xx провайдера | переключение на резерв из `model-candidates.md` §4 или отказ с сохранением сырого текста; публикации нет |
| Исчерпан бюджет токенов | срабатывает деградация: страница не генерируется, ВК и письмо остаются (ожидаемое поведение из §4 `model-candidates.md`) |
| ВК отвечает 429 или ошибкой | повтор с ограничением, статус «не отправлено», не «отправлено» |
| SMTP недоступен | то же; письмо не теряется |
| Публикация без approve | 4xx, вызова ВК и SMTP не было (счётчик заглушки = 0) |
| Правка после публикации (если P5 решён «в объём») | перегенерация меняет только изменённые поля, все площадки обновлены, `E1` перегенерации ≤ 2 мин |
| Две параллельные заявки разных экспертов | данные не смешиваются, токены ВК разных экспертов не пересекаются |
| Спецсимволы в `title` (`\r\n`, `<script>`, `]]>`) | заголовок письма без переводов строк, страница экранирует |
| Миграции БД | чистая БД поднимается, `down`/`up` без потери схемы |

### 2.3 Evals (настоящая модель)

| Набор | Что считаем | Метрики |
|---|---|---|
| `v1.jsonl`, split `dev` | M1 по полям, M2, M3, M6 | считаются при каждом изменении, смотрятся разработчиком |
| `v1.jsonl`, split `test` | то же | только перед сдачей лабы; обращения записываются в CHANGELOG |
| `adversarial.jsonl` | S1; `forbidden_strings` в полях и постах; `must_not_call` | S1, S2 |
| тексты постов по всем записям | линтеры M7; judge M4, M5 по бинарному чек-листу | M4, M5, M7 |
| трейсы запросов | p50 и p95 времени, стоимость | E1, E2, E3 |
| `needs_context` (2 записи) | отдельная строка отчёта | не входят в M1–M3 до решения по P5 |

Правила проведения прогона:

- температура 0; на каждую запись **3 повтора** (как в lab1), в отчёте доля стабильных ответов и результат по большинству;
- «сегодня» для модели = `published_at` записи, реального времени не использовать;
- в отчёте `n`, интервал Wilson 95%, `dataset_version`, `prompt_version`, `model_id`; приёмка по нижней границе интервала (`success-criteria.md` §8);
- судья M4, M5 прежде проходит калибровку на 20 примерах, доля совпадений с человеком ≥0.8, иначе его переписывают.

### 2.4 Вручную и вне CI

Интервью с экспертами, калибровка judge, ручная сверка спорных случаев M5, красная команда лабы 4, замер T1 на пилоте, проверка визуального вида страницы. Результаты фиксируются ссылкой в PR.

## 3. Метрика → уровень → когда

Каждая из 15 метрик привязана к одному месту, где она считается.

| Метрика | Уровень | Где считается | Блокирует PR |
|---|---|---|---|
| M1 Field Accuracy | evals | `evals`, dev | нет, сравнение (F2 для критичных) |
| M2 Critical Field Error Rate | evals | `evals`, dev | **да**, верхняя граница не выше baseline |
| M3 Full Extraction Accuracy | evals | `evals`, dev | нет, для сравнения версий промпта |
| M4 Edit-free Rate | evals + пилот | judge, затем логи редактора | нет |
| M5 Hallucination Rate | evals | judge + ручная сверка | нет, до baseline |
| M6 False-fill Rate | unit + evals | `unit` (правило), `evals` (на датасете) | **да**, верхняя граница не выше baseline |
| M7 Format Compliance | unit + evals | `unit` (линтер), `evals` (на реальных постах) | **да**, 100% |
| M8 Page Assembly Correctness | unit + интеграция | `unit`, `integration` | **да**, 100% |
| M9 Media Integrity | unit + интеграция | `unit`, `integration` | **да**, 100% |
| T1 Time-to-publish | пилот | хронометраж | нет |
| E1 Latency | evals + интеграция | трейсы | нет, публикуется p50 и p95 |
| E2 Cost per request | evals | логи токенов | **да**, потолок PRD: 10 ₽ и 3 ₽ |
| E3 Success Rate | интеграция + evals | логи | нет, до baseline |
| S1 Injection Resistance | evals | `adversarial.jsonl` | **да**, нижняя граница не ниже предыдущей |
| S2 Pre-publication Gate | unit + интеграция | тесты gate | **да**, 100% |

«Блокирует PR» совпадает с жёсткими и сравнительными критериями F2–F9 в `dod.md` §4.

## 4. Что гоняем в CI (с лабы 3)

Текущий `ci.yml`: `structure`, `compose`, `docs`, `future-checks` (заглушка). Предлагаемый набор джоб (критерий D2 в DoD):

| **Джоба CI (Oтдельная задача внутри CI)** | Содержимое                                                           | Когда                                                                                    | Секреты       | Падение блокирует merge                         |
| ------------------------------ | -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ------------- | ----------------------------------------------- |
| `structure`, `compose`, `docs` | остаются как есть                                                    | каждый PR                                                                                | нет           | да                                              |
| `lint`                         | ruff, форматирование, проверка типов                                 | каждый PR                                                                                | нет           | да                                              |
| `unit`                         | все unit из §2.1                                                     | каждый PR                                                                                | нет           | да                                              |
| `dataset-validate`             | `validate_golden.py` + негативный тест валидатора                    | каждый PR, при изменениях в `docs/quality/golden-dataset/**` обязательно                 | нет           | да                                              |
| `integration`                  | §2.2 на fixtures и заглушках, Postgres как сервис                    | каждый PR                                                                                | нет           | да                                              |
| `secrets`                      | gitleaks                                                             | каждый PR                                                                                | нет           | да                                              |
| `evals-fast`                   | dev-подмножество (25 записей) + adversarial (9), 1 повтор, без judge | PR, меняющий `services/extractor/**`, промпты, схему, датасет; либо по метке `run-evals` | `LLM_API_KEY` | да: по жёстким порогам из §3                    |
| `evals-full`                   | весь датасет, 3 повтора, judge                                       | ночью и перед сдачей лабы                                                                | `LLM_API_KEY` | нет; результат в отчёт, регрессия заводит issue |

Что не гоняется в CI и почему: красная команда лабы 4 (долго, нужен человек), калибровка judge (разово), T1 и M4 (данные пилота), визуальная проверка страницы. PR из форков не получают секретов, поэтому `evals-*` для них пропускаются, а merge идёт только после прогона мейнтейнером.

Отчёт каждого прогона evals: машиночитаемый JSON `docs/quality/reports/<дата>-<prompt_version>.json` + таблица в markdown; артефакт джобы и ссылка в PR (F1, F10).

## 5. Блокирующие и информационные проверки

- **Жёсткие (любое отклонение = баг):** unit, интеграция, валидатор датасета, gitleaks, M7, M8, M9, S2 = 100%.
- **Сравнительные:** M2, M6, S1 по границам интервалов Wilson. Прогон без отчёта предыдущей версии не считается выполненным.
- **Потолок:** E2 (10 ₽ и 3 ₽ из PRD).
- **Информационные до baseline:** M1, M3, M4, M5, E1, E3. Цель и порог ставятся после первого прогона (правило `success-criteria.md` §7), до этого блокировать нечем, это называется честно.

## 6. Стоимость и стабильность прогонов

Оценка по `model-candidates.md` (GPT-4o-mini, ≈0.052 ₽ на комплект из 3 текстов):

| Прогон | Вызовов | Оценка |
|---|---|---|
| `evals-fast`: 34 записи × 1 | 34 | ≈1.8 ₽ |
| `evals-full`: 44 записи × 3 | 132 | ≈6.9 ₽ + judge (≈ ×2) → до 20 ₽ |

Оценка верхняя, замер заменит её (A9). Если провайдер заменён на YandexGPT Pro 5 (≈1.44 ₽ на комплект), `evals-full` обойдётся примерно в 190 ₽ + judge, поэтому он идёт ночью, а не на каждый PR.

Нестабильность. Ответ модели при температуре 0 не гарантированно детерминирован. Поэтому: 3 повтора, учёт по большинству, доля «нестабильных записей» публикуется в отчёте; запись, меняющая ответ в 3 повторах, помечается и разбирается, а не перезапускается до зелёного.

## 8. Открытые вопросы

1. Резолвер относительных дат: делает модель или код. Если код, большая часть M1 по `date_start` переходит в unit и становится детерминированной. Предлагаю код, решает AI Engineer.
2. Fixtures LLM: кто и как часто их обновляет. Предложение: AI Engineer при смене промпта, в одном PR с отчётом evals.
3. Тариф провайдера для E2 (Delivery): без него E2 в CI не считается.
4. Какой резервный провайдер должен проходить evals: если YandexGPT Pro 5 объявлен обязательным резервом (`model-candidates.md` §5), его `evals-full` нужно прогнать хотя бы раз до релиза.
5. Что значит «публикация прошла» для ВК и рассылки, когда сервис площадки принял запрос, но доставка асинхронна: влияет на статус и на S2.
6. До появления кода все ссылки на тесты в этом плане — требования к будущим тестам, а не существующие файлы.
